# Hatch visual and workflow review

Review date: 2026-10-03  
Reference: `DESIGN.md` and the accepted decisions in `DECISIONS.md`  
Method: disposable in-memory project, 21 synthetic tickets spanning all 16 statuses and all four turn colors, proposal and sketch data, a question with answers, Specs, decision, previews, worktrees, agent runs, and successful and failed sync entries. The snapshot harness ran every captured route in light and dark appearance. It captured 24 view states in both appearances (48 PNGs) to `/tmp/hatch-final-audit-v5/`, using an in-memory demo project. It does not use the Hatch database or probe GitHub/Claude credentials.

## Cross-screen findings

- The live application screenshot shows the selected sidebar row as a normal system selection. The bitmap snapshots show a black sidebar column, so that black area is a capture artifact and must not be “fixed” in the app.
- Light and dark appearances keep the system typography and status colors readable. Active turns use amber or teal; neutral metadata stays subdued. The embedded sketch sample has its own light background in both modes, as expected for the fixed CSS in that HTML fixture.
- The toolbar uses icon-only Search, New Ticket and Ask controls with shortcut help. The project selector is now a SwiftUI `Menu`, with the project name and tile retained in its label and checkmarks identifying the selection. Ask uses a conditionally presented SwiftUI `HSplitView`; its built-in divider makes the inspector width adjustable. The app builds and the populated light/dark snapshots complete.
- The route screenshots use realistic, but synthetic, records. No private ticket contents were read into the fixtures and no GitHub writes occur in snapshot mode.
- The command-palette capture uses a demo-only presentation of the sheet contents; it does not show the dimmed parent window. Ask is captured through its regular ticket context in the resizable split pane. `View > Ask Inspector` and Control-Command-I toggle the pane.
- Stage’s `--snapshots` harness captured 13 states per appearance using its in-memory demo data source. The center specimens and toolbar are visible, while the side panels are partly clipped or black and attached sheet snapshots are black; those panels need live-window inspection before their spacing can be called verified.

## Verification and remaining work

- The app builds locally with `xcodebuild -project Hatch.xcodeproj -scheme Hatch -destination 'platform=macOS' build`; the snapshot run completed and wrote 48 populated Hatch images. `cd Stage && swift build` passes with the Stage `--snapshots` harness; it wrote 26 images across 13 states in both appearances.
- The snapshot captures are synthetic bitmap output, so Liquid Glass appearance cannot be judged from them. The live Hatch app's toolbar and glass controls were checked earlier on the owner's Mac in both appearances. Stage capture has black or cropped side panels and black attached sheets, so those areas remain visually unverified. The Hatch contact sheets are `/tmp/hatch-final-audit-v5/contact-light.jpg` and `/tmp/hatch-final-audit-v5/contact-dark.jpg`; individual PNGs are in `/tmp/hatch-final-audit-v5/`. Modal confirmation sheets for Iris, ticket drop, and Preview discard are not yet captured.
- The native SwiftUI `.inspector(isPresented:content:)` and `InspectorCommands` APIs were checked against current Apple documentation. See [Apple HSplitView documentation](https://developer.apple.com/documentation/swiftui/hsplitview), [Apple inspector modifier documentation](https://developer.apple.com/documentation/swiftui/view/inspector%28ispresented%3Acontent%3A%29), and [Apple InspectorCommands documentation](https://developer.apple.com/documentation/swiftui/inspectorcommands).
- GitHub device authorization remains unverified until the owner approves registering and installing the app. The private demo repository exists; the integration Client ID is still a placeholder. The earlier CLI-based sync check used a disposable database and does not verify the new browser sign-in.
