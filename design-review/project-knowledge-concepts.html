Where a project's knowledge lives

You asked whether "Design system" is where design decisions, architecture, agent instructions and specimens live. It is not. It holds only the app's visual building blocks. Below: where each thing lives today (from the code), the gaps I found, my proposal, what should not move, names, and how the workflow changes. The questions at the bottom are answerable here, as before.

Decisions (written when you accept a Proposal), picks and notes, history, agent runs, claims and previews. Nothing here is in git or on GitHub.

Inside Hatch itself

The agent rules for each task (Prepare, Build, Fix, Iris) are written in Hatch's code, so no agent has to remember a procedure. Project-specific guidance is only the flat docs list.

Gaps I found

1. Decisions exist only on this Mac. They are rows in the local database. A new Mac, a reset or a second person loses the "why" behind every choice. Agents can't read them either.

2. Architecture and coding decisions have no home. A Decision is only created when you accept a visual Proposal. "We use actors for connections" or "no Combine in new code" is recorded nowhere that agents read.

3. Agent guidance is one flat list of files. A Build agent and a Prepare agent get the same docs, and there's no place for "how we write code in Echo" beyond CLAUDE.md.

4. The setup leaves agents without folders. Build tasks also work in the design system repository and Prepare tasks in the specimens repository, and both need a clone on this Mac. The assistant sets neither, so hatch take would say "no local clone configured". I'll fix this in any case.

Proposal: one project notebook

One private repository per project that holds what Hatch and you decide, as plain files that you, agents and git can read: echo-hatch. Hatch creates it during setup, keeps a clone on this Mac, and is the only one that writes to it, except for the option code agents put in specimens/.

A decision file

--- ticket: 151 kind: design spec: [TOAST-3] decided: 2026-10-04 --- # Toast spacing Chose B, 12pt between icon and text. Why: A felt cramped at large type; C wasted width. Options: A 8pt, B 12pt, C 16pt.

Indexed for search like the Spec. Iris checks new tickets against it ("#151 already decided this").

What should not go in the notebook

The Spec stays in the app repository. It describes what the code does and must change in the same pull request as the code. A ticket can't be Done until its Spec is updated.

The components package stays its own, versioned thing. The app depends on a tagged version of it. Folding it into the notebook would make the app depend on Hatch's files.

Tickets, threads and screenshots stay in the tickets repository. Issues need it, and it's shared across projects.

Live state stays in Hatch's database: picks in progress, claims, agent runs, token costs and the log. They change every minute and are only useful on this Mac. Only the final decision is written to the notebook.

Hatch's own rules stay in Hatch's code. The procedure for each task (take, plan, ready) is enforced by the app, not written in a guide an agent might skip. Guides add project knowledge on top.

How the workflow changes

Deciding

Every decided Proposal, Sketch or Question writes a decision file of kind design, architecture or workflow. A Question can carry options A/B/C with a recommendation, like this page, so architecture choices are made the same way as visual ones. There are still six ticket types.

Briefing agents

hatch take gives each task its guides (Build and Fix get code.md, Prepare gets design.md) and the decisions for the ticket's area. That replaces the flat docs list.

Vetting

Iris already compares new tickets with other tickets and the Spec. She also compares them with decisions, and flags a ticket that would undo one.

Setup

The assistant gets a Notebook step (Hatch creates echo-hatch, private), and the components step finds or clones its folder too. Specimens is no longer a separate repository.
