Where a project's knowledge lives

You asked whether "Design system" is where design decisions, architecture, agent instructions and specimens live. It is not. It holds only the app's visual building blocks. Below: where each thing lives today (from the code), the gaps I found, my proposal, what should not move, names, and how the workflow changes. The questions at the bottom are answerable here, as before.

Where things live today

#

Tickets repository

Issues are tickets, and labels hold their type, status and project. Comments are the thread. Screenshots go in attachments/. Shared by all projects.

The code, plus .hatch/project.json (settings and the area index) and .hatch/spec/*.md (the Spec: what the app does, by area). Also any docs you list for agents, such as CLAUDE.md.

▤

Hatch's database, on this Mac

Decisions (written when you accept a Proposal), picks and notes, history, agent runs, claims and previews. Nothing here is in git or on GitHub.

⚙

Inside Hatch itself

The agent rules for each task (Prepare, Build, Fix, Iris) are written in Hatch's code, so no agent has to remember a procedure. Project-specific guidance is only the flat docs list.

Gaps I found

1. Decisions exist only on this Mac. They are rows in the local database. A new Mac, a reset or a second person loses the "why" behind every choice. Agents can't read them either.

2. Architecture and coding decisions have no home. A Decision is only created when you accept a visual Proposal. "We use actors for connections" or "no Combine in new code" is recorded nowhere that agents read.

3. Agent guidance is one flat list of files. A Build agent and a Prepare agent get the same docs, and there's no place for "how we write code in Echo" beyond CLAUDE.md.

4. Hatch's database is the only record of a lot. Picks, the state of Proposals and where work stands all live in it. Without Hatch, nothing tells an agent where you were.

5. The setup leaves agents without folders. Build tasks also work in the design system repository and Prepare tasks in the specimens repository, and both need a clone on this Mac. The assistant sets neither, so hatch take would say "no local clone configured". I'll fix this in any case.

The test it has to pass

April 2027. Hatch is gone or you're on another machine. You clone echo-notebook next to the app, open any agent (Claude Code, Codex, Cursor) and say "pick up where we left off". With nothing else, the agent must be able to answer:

What is this project, and where is its code? · What's in flight, what's waiting for me, what's next? · What did we decide, and why? · How do we work: branches, reviews, shipping? · What did we try and reject? · How do I continue a half-done Proposal?

That gives the rule everything below follows: nothing that matters lives only in Hatch. Hatch's database becomes a fast cache. The truth is plain files in git (the notebook and the app repository) and GitHub issues. Hatch writes those files for you, so keeping them current costs you nothing.

Proposal: the app stays clean, the notebook holds the rest

Agent files are often kept out of the app repository (gitignored, or the app is public). So the app repository gets no Hatch files at all. Everything Hatch and agents need, coding rules included, lives in the notebook, and Hatch places the rules where agents look.

tashda/echo-notebook private
├─ README.md what Echo is, its repositories, how to start
├─ AGENTS.md for an agent opened in the notebook
├─ WORKFLOW.md how work flows, with or without Hatch
├─ NOW.md in flight, waiting for you, next up
├─ project.json settings and area index (was .hatch/ in the app)
├─ rules/
│  ├─ AGENTS.md how we write code in Echo: short
│  └─ areas/connections.md detail, read only when the area is touched
├─ spec/ what the app does, by area (was .hatch/spec)
├─ decisions/ one file per decision + index
└─ specimens/ Proposal options, Echo today

tashda/echo only the app's code
└─ AGENTS.md, CLAUDE.md placed by Hatch, never committed

How the rules reach every agent

When Hatch sets up the clone, and every time it makes a worktree for a ticket, it copies rules/AGENTS.md in as AGENTS.md, with a CLAUDE.md that says @AGENTS.md (Claude Code's import). It also lists both in the clone's .git/info/exclude. They can never be committed, even if the app's .gitignore doesn't mention them, and the app's .gitignore is left alone. A worktree doesn't copy untracked files, which is why Hatch places them each time.

If the app already commits its own AGENTS.md

Hatch leaves it alone and doesn't place its copy. The notebook's rules then go in the brief instead. Setup tells you which case you're in.

Picking up without Hatch

The notebook's README starts with one line: "Copy rules/AGENTS.md into your clone of the app as AGENTS.md." Everything else is readable as it is.

Spec and settings move to the notebook too

With no Hatch files in the app, .hatch/project.json and .hatch/spec/ move to the notebook. The cost: the Spec no longer sits in the same pull request as the code. Hatch makes up for it. A ticket already gets a ticket/151-… branch in each repository it touches; the Spec change goes on the notebook branch, and the existing rule (no Done until the Spec is updated or marked unchanged) is checked across both. The merge plan already merges several repositories per ticket.

Risk: someone changes the app outside Hatch and the Spec drifts. Hatch can flag commits on dev that touch an area without a matching Spec change.

Why this keeps tokens low

Hatch writes the notebook

Decision files, NOW.md and WORKFLOW.md are filled from data Hatch already holds: the options, your pick and your reason. No model call, so writing them costs zero tokens.

Free search picks the context

Before an agent starts, local FTS selects the few Spec items and decisions that match the ticket's area. The agent reads those, not the whole notebook. Agents never call GitHub; hatch answers from SQLite.

Short rules, detail on demand

The AGENTS.md an agent loads every session stays short. Area detail is a path the brief names, read only when that area is touched. Today's flat docs list makes every agent read everything.
