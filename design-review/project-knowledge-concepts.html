Where a project's knowledge lives

You asked whether "Design system" is where design decisions, architecture, agent instructions and specimens live. It is not. It holds only the app's visual building blocks. Below: where each thing lives today (from the code), the gaps I found, my proposal, what should not move, names, and how the workflow changes. The questions at the bottom are answerable here, as before.

Where things live today

#

Tickets repository

Issues are tickets, and labels hold their type, status and project. Comments are the thread. Screenshots go in attachments/. Shared by all projects.

{}

App repository

The code, plus .hatch/project.json (settings and the area index) and .hatch/spec/*.md (the Spec: what the app does, by area). Also any docs you list for agents, such as CLAUDE.md.

◐

"Design system" repository

Only EchoDesignSystem: colors, type and components, as a tagged Swift package. The Stage imports it so options look real. It is merged first when work ships.

◫

Specimens repository

The Swift code of each Proposal's options, plus the shared "Echo today" views. Agents prepare Proposals there. The setup does not ask for it yet.

▤

Hatch's database, on this Mac

Decisions (written when you accept a Proposal), picks and notes, history, agent runs, claims and previews. Nothing here is in git or on GitHub.

⚙

Inside Hatch itself

The agent rules for each task (Prepare, Build, Fix, Iris) are written in Hatch's code, so no agent has to remember a procedure. Project-specific guidance is only the flat docs list.

Gaps I found

1. Decisions exist only on this Mac. They are rows in the local database. A new Mac, a reset or a second person loses the "why" behind every choice. Agents can't read them either.

2. Architecture and coding decisions have no home. A Decision is only created when you accept a visual Proposal. "We use actors for connections" or "no Combine in new code" is recorded nowhere that agents read.

3. Agent guidance is one flat list of files. A Build agent and a Prepare agent get the same docs, and there's no place for "how we write code in Echo" beyond CLAUDE.md.

4. Hatch's database is the only record of a lot. Picks, the state of Proposals and where work stands all live in it. Without Hatch, nothing tells an agent where you were.

5. The setup leaves agents without folders. Build tasks also work in the design system repository and Prepare tasks in the specimens repository, and both need a clone on this Mac. The assistant sets neither, so hatch take would say "no local clone configured". I'll fix this in any case.

The test it has to pass

April 2027. Hatch is gone or you're on another machine. You clone echo-notebook next to the app, open any agent (Claude Code, Codex, Cursor) and say "pick up where we left off". With nothing else, the agent must be able to answer:

What is this project, and where is its code? · What's in flight, what's waiting for me, what's next? · What did we decide, and why? · How do we work: branches, reviews, shipping? · What did we try and reject? · How do I continue a half-done Proposal?

That gives the rule everything below follows: nothing that matters lives only in Hatch. Hatch's database becomes a fast cache. The truth is plain files in git (the notebook and the app repository) and GitHub issues. Hatch writes those files for you, so keeping them current costs you nothing.

Why coding rules go in the app, not the notebook

Agents read AGENTS.md in the repository they work in. Codex, Cursor and others read it directly, and Claude Code reads CLAUDE.md, which can point to it. An agent fixing a bug in Echo never opens the notebook, so "no Combine in new code" has to sit next to the code, or a non-Hatch agent breaks it.

Why the rest goes in the notebook

Decisions, work in flight and specimens are about the project, not the code. Kept in the app repository they'd clutter its history and pull requests. Kept on this Mac they'd fail the test.

What each file holds, and who writes it

README.md: the project in a paragraph, links to the app, components and tickets repositories, and "clone these, read AGENTS.md". Written at setup, updated when repositories change.

AGENTS.md (notebook): the order to read things in, what each file is for, and the rule that Hatch's commands are used when Hatch is running and WORKFLOW.md is followed when it isn't.

WORKFLOW.md: the process Hatch enforces, in words. A ticket per change, a ticket/151-… branch, plan before big changes, build before review, merge into hatch, a pull request to dev, Spec updated before Done. Generated from the same rules Hatch runs, so the two never disagree.

NOW.md: the open tickets grouped by turn (waiting for you, agents working, queued), each with one line on where it stands, plus the last ten decisions. Refreshed by Hatch on every status change. GitHub issues still hold the full text.

decisions/: one file per decision in the common ADR shape (context, options, decision, why, consequences), with ticket, kind, area and Spec IDs at the top. Written when a Proposal, Sketch or Question is decided, and never edited afterwards. A later decision says which one it replaces.

specimens/: each Proposal's option code, with a short README of what was compared and what won. Rejected options stay, so "what did we try" has an answer.

What should not go in the notebook

The Spec stays in the app repository. It describes what the code does and changes in the same pull request as the code.

Coding rules stay in the app's AGENTS.md, for the reason above.

The components package stays its own, versioned repository. The app depends on a tagged version of it.

Full ticket text, threads and screenshots stay in GitHub issues. NOW.md is a summary, not a second copy that could disagree.

Live and noisy state stays in Hatch's database: picks in progress, claims, agent runs, token costs and the log. None of it is needed to pick up again.

Is this the best way to work?

For agents

Each agent reads the AGENTS.md where it works, and Hatch's brief adds the ticket, the area's decisions and Spec. The context is short and on point (the cost rule), with no long list of docs to read.

For shipping

Nothing changes in the path to dev: ticket branch, hatch, CI, pull request. Decisions are written as a side effect of deciding, so there's never a documentation chore before a release.

For picking up later

Two clones and one sentence to any agent. Everything is plain Markdown and Swift in git. No database, no app and no special format is needed to read it.
