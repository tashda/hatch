Settings: the Agents page

A proposal for how the Agents page should look and behave, and the rules for macOS controls that every Settings page will follow. First what is wrong today, then the proposed page, the menus behind each control, a general way to organise providers that works for everyone, Add provider as a sheet, and "agents at once". The questions at the bottom can be answered on the page.

What is wrong today

Too much in each row

A task has a title, a description, a Test button, two pickers, a billing line, and a paragraph of recommendation, all in one block. A provider row has a switch, two status lines, refresh, Test, Edit… and a ⋯ menu. The eye has nowhere to rest.

Paragraphs inside rows

The four-line recommendation under Iris is useful the first time and noise every time after. System Settings keeps rows to a label and a value, and puts explanations in one short footer under the section.

Two pickers for one choice

Provider and model are picked separately, but you think of them as one thing ("Haiku via Claude Code"). The model menu shows ids like "haiku (typed)" and "Program default", which mean nothing without reading the code.

Controls that are not Apple's

"Max agents at once: 3" puts the value in the label, with a tall stepper at the far edge. "Add provider" is a split button with a long, unsorted menu of 13 items. Edit… opens a form that mixes program paths, keys and models.

The rules for every Settings page

Apple's own grammar, as System Settings uses it. Once agreed, every page follows it and new pages need no design round.

NeedControlRule
The pageOne grouped FormSections with a short title. At most one footer sentence or two per section, never paragraphs in rows.
Choose one of a listHaiku Picker in a Form rowLabel on the left, value and the round chevron on the right, with hover. Never a bordered box, never a value inside the label.
On or off SwitchTrailing in the row. For a whole thing (a provider) the switch sits on its row.
A small number3 Picker with the useful valuesA few sensible numbers in a menu, the recommended one marked. A stepper only for numbers that change by one many times.
A thing with detailsRow with i or "Details…"Opens a sheet with everything about that thing: settings, Test, Remove. The row itself shows only name, status and its switch. This is how Internet Accounts and Users & Groups work.
Adding a thing"Add…" button at the end of the list → sheetA sheet that asks only what is needed for the kind chosen. Never a long menu.
StatusSecondary text under the row titlePlain words ("Signed in with your Claude plan"). Colour only when something is wrong.
Recommendation"Recommended" in the menu item, reason in the footerThe owner's rule (one recommendation and its reason) kept, in one line, where the choice is made.
TestInside the details sheet, and one "Test All" per sectionThe result appears as the row's status, not as an extra block.

What moved where

Provider and model are one picker. Effort and thinking show as their own row only when the chosen model has them. Recommendations are one footer line. Test, refresh, Edit and Remove live in the provider's details sheet. "Used by" is the provider's status line.

Why "Coding agents" is its own section

The agents that build tickets are a different job from Iris and Ask. They run a program in a copy of your code, and you choose which program and how many at once. Today that choice is hidden; only the number is shown.

Only providers that run a program can build tickets: they edit files in a worktree. API-only providers are not offered here.

Providers for everyone, not one setup

Today's Add menu is a list of setups: "Claude Code with GLM (Z.ai Coding Plan)", "Z.ai GLM API key", "Gemini API key". Each new service or combination would need another item, and the list reflects one person's setup. Instead, every provider is one of three ways to reach a model, and the services are data under them. Your setup (Claude plan, GLM through Claude Code, Z.ai key) is then just three ordinary entries.

⌘

A program you are signed in to

An agent program on this Mac: Claude Code, Codex, Gemini CLI, opencode. It uses its own sign-in (your plan), or is pointed at an API (see below). Only programs can be coding agents: they edit files.

Your GLM setup: Claude Code, signed in through an Anthropic-compatible endpoint, with Z.ai chosen from the known services.

⇄

An API service with a key

Billed per token. A service speaks one of two languages: Anthropic or OpenAI-compatible. Known services (Anthropic, OpenAI, OpenRouter, Z.ai, Gemini, Mistral, DeepSeek, Groq and more) fill in the address, the key's variable name and a link to create a key. Anything else is "Custom" with an address.

▣

A server on this Mac or network

Ollama, LM Studio, llama.cpp and other OpenAI-compatible servers. Hatch looks for them on their usual ports and lists what it finds with its models. Anything else is "Custom" with an address. No bill.

Why this holds up

A new service is a line of data (name, language, address, key variable, link), not new screens. A program can be pointed at any service that speaks its language, so "Claude Code with GLM", "Claude Code with Kimi" or "Claude Code through a company proxy" all work without special cases. The list of services ships with Hatch and can be updated without changing the app's design.
