The agent launcher

Today you start Claude Code yourself and it calls hatch take. With a launcher, Hatch starts the agent itself: it claims the ticket, makes its workspace, places the rules, writes the brief, and runs the program with the task's model and effort (Prepare, Build or Fix). What already exists and is reused: claiming and workspaces, the brief, the push guard that allows only ticket/… branches, "Agents at once", and the run records with tokens. Five decisions, each with my recommendation.

1. When does an agent start?

A · RECOMMENDED: BY ITSELF, WITH A PAUSE SWITCH

When a ticket is ready for an agent (Ready, Accepted, or back from your review) and a slot is free, Hatch starts one. A Pause switch in the toolbar and in Settings stops new starts; running agents finish. This is what "Agents at once" was always for.

B · WHEN YOU PRESS START

Each ticket gets a Start Agent button. Full control, but work waits for you, and the slots only limit what you start.

C · BY ITSELF FOR SMALL WORK ONLY

Tweaks and Bugs start by themselves; Proposals and Builds of accepted Proposals wait for Start. A middle way while you build trust.

2. Which programs can run as agents?

A · RECOMMENDED: CLAUDE CODE FIRST, CODEX NEXT

Claude Code runs headless in the workspace with the task's model and effort, and reports tokens. Codex follows with its own headless mode. Gemini CLI and opencode can be picked for coding tasks only once they are supported; until then the Settings menu shows them as "not yet for coding".

B · ALL FOUR AT ONCE

Every program from day one. Four sets of flags, permissions and output formats to get right before anything works.

3. What may an agent do on this Mac?

A · RECOMMENDED: ITS WORKSPACE, ITS TOOLS, NOTHING ELSE

It may edit files in its own workspace, run the build and test commands, git (push only to its ticket/… branch, already enforced), and the hatch commands. Everything else is refused without asking you, so an agent never blocks waiting for permission.

B · FULL FREEDOM IN THE WORKSPACE

The program's "skip all permission checks" mode. Never blocks and never refuses, but nothing stops a command outside the workspace.

C · ASK ME

Each new kind of command waits for your yes in Hatch. Safest, but agents stand still whenever you are away.

4. Where do you watch an agent?

A · RECOMMENDED: THE TICKET'S WORK TAB

The ticket shows the agent's steps and a live log, with Stop and "Open in Terminal" to take over in its workspace. The Agents page lists every running agent with its ticket, model, time and tokens. (The Agents page belongs to the other session; I would only add the running list.)

B · A TERMINAL WINDOW PER AGENT

Each agent runs visibly in Terminal. Familiar, but windows pile up and Hatch cannot show progress itself.

5. When an agent stops without finishing

A · RECOMMENDED: ONE RETRY, THEN IT WAITS FOR YOU

If the program exits or times out before hatch ready or hatch offer, Hatch keeps the workspace, notes what happened on the ticket with the end of the log, and starts it once more. A second failure puts it on your Desk with the reason.

B · IT WAITS FOR YOU AT ONCE

No retry; the first failure goes to your Desk. Fewer tokens spent on a ticket that keeps failing.
